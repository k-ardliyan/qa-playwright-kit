Sebelum framework

Sharing ini untuk siapa?

Untuk QA, developer, dan lead yang ingin mengubah kebutuhan bisnis menjadi regresi yang bisa dijalankan, dibaca, dan diputuskan bersama.

requirement · test · evidence · decision

QA

Memperjelas skenario

Menentukan risiko, role, data, dan hasil yang observable.

Developer

Menerima bukti yang utuh

Melihat langkah, actual result, source kegagalan, dan attachment.

Lead

Mengambil keputusan

Memisahkan bug aplikasi dari masalah test, environment, atau requirement.

Target sesi: paham alur dan batasnya, bukan menghafal API Playwright.

Kemampuan 1/4

Kebutuhan sebagai Kontrak

Struktur yang bisa dicek mesin, dan tetap enak dibaca manusia.

Metadata wajib

Tag, Prioritas, Auth state, Halaman awal
Module: wajib, error bila kosong
Feature: disarankan, warning bila kosong
Role scope + Access expectation

Tag skenario = cara pengujian

@success @failure @access-restriction @network @hybrid @aria @visual @manual @download @upload @file-content @network-assert
Kenapa wajib? Kebutuhan yang ambigu ditolak di awal. Hasil harus bisa diamati: jadi test tidak pernah "abu-abu".

Kemampuan 2/4

Toolkit QA yang Sudah Jadi

Bantuan tipis di atas API resmi Playwright: tinggal pilih tag, alatnya otomatis dipakai.

@network: simulasi

Respons palsu untuk uji error, kosong, atau data tetap

@hybrid: hibrida

Data lewat API, hasil dicek di layar. Cepat & stabil

@aria: struktur

Cek "bentuk" halaman via struktur aksesibilitas

@visual: gambar

Bandingkan screenshot dengan baseline, tangkap regresi

Form lembut

Banyak pesan error dicek sekaligus dalam satu formulir

Jam (clock)

Atur waktu aplikasi untuk menguji tanggal tertentu

Dan validator memastikan setiap tag punya alat yang sesuai di kode: jadi tidak ada test "palsu".

Kemampuan 3/4

Kartu Masuk
Per Peran

Peran tunggal

TEST_USER_EMAIL=... TEST_USER_PASSWORD=... → .auth/local/user.json

Banyak peran

FINANCE_EMAIL=... HRD_EMAIL=... → .auth/local/finance.json → .auth/local/hrd.json

Gampangnya: test finance pakai kartu finance, test HRD pakai kartu HRD: tidak pernah tertukar. Role ditemukan dinamis dari environment; secret keys otomatis dienkripsi saat setup. Perubahan berikutnya lewat npm run env:edit.

Sebelum minta pipeline

Checklist requirement yang siap

Struktur

✓ Module · Feature · Tags

Auth state, halaman awal, prioritas, dan role scope terisi sesuai konteks.

Traceability

✓ AC-XX · SC-XX · Test ID

Setiap scenario menyebut Covers dan punya hubungan yang bisa ditelusuri.

Input

✓ Provenance jelas

seed:, credential:, fixture:, atau literal:; bukan secret mentah.

Expected

✓ Observable

URL, text, visibility, status, file content, atau bukti lain yang bisa dicek.

Rule of thumb: jika reviewer tidak bisa membayangkan bukti pass/fail-nya, requirement belum siap di-Plan.
